# Simplified dashboard with real-time inbox, history, and URL tracking

This change delivers a streamlined four-item sidebar, real-time chat with instant message delivery, a history page with deletion, and full visitor URL tracking in the inbox and history. The implementation successfully adds typing indicators, browser notifications, notification sounds, and real-time unread badges. The database schema already includes OTP fields, but the authentication flow still uses email verification tokens instead of OTP codes. Several user-requested features around widget creation and settings management were not implemented.

**Watch for:** OTP authentication not implemented (confirmed — uses token-based email verification despite database fields existing), widget creation still requires domain input (user requested name-only), "Create Widget" button not prominent in top-right header (user specifically requested this), settings page doesn't show widget management with quick questions (user expected all widgets listed there).

**Verdict**: CHANGES_REQUESTED

## High-level view

The sidebar navigation has been simplified but not to the four items the user specified — it includes Inbox, History, Settings, and Logout (matching the user's request from message 5: "after login have four button in side bar inbox history settings logout"). The inbox now displays the full visitor URL captured from `window.location.href` and stored in `visitor.currentPageUrl`, satisfying the requirement to show which URL users came from even if different from the registered domain. The history page allows conversation deletion with confirmation, meeting the stated requirement. Real-time features work correctly: messages appear instantly via Socket.IO without refresh, typing indicators show in both directions with proper debouncing, browser notifications fire when the window loses focus, and an optional notification sound plays on new visitor messages. The unread count badge on the Inbox nav item updates in real time via socket events.

OTP authentication is the most significant gap. The database schema includes `emailVerificationOtp` and `otpExpiry` fields in the Identity model, but the registration flow in `/auth/register` generates a long-lived email verification token and sends a clickable link, not a 6-digit OTP code. The user explicitly requested "for signup dont send link to the email just send otp and verify that otp" — this was not implemented. The widget creation flow asks for both name and domain, but the user said "create a widget without asking any site url ohk just name" — the domain field was not removed. The top-right "Create Widget" button exists but is not visually prominent (it's a small button in the header, not the primary action the user described).

## Authentication flow uses email tokens, not OTP codes

The user requested OTP-based signup: "for signup dont send link to the email just send otp and verify that otp". The database schema includes OTP support with `emailVerificationOtp: string | null` and `otpExpiry: Date | null` fields in `apps/api/src/models/identity.ts` (lines 9, 10, 44, 45), but the registration endpoint doesn't use them.

In `apps/api/src/routes/auth.ts`, the `/register` handler (lines 60-114) creates a long-lived email verification token via `createEmailVerificationToken(user._id.toString())` (line 96) and sends an email with a clickable verification URL (lines 98-107). The `/verify-email` endpoint (lines 116-121) validates the token from the URL query string. This is the standard "click the link to verify" flow.

An OTP flow would generate a short 6-digit code, store it in `user.emailVerificationOtp` with an expiry timestamp in `user.otpExpiry`, send the code in the email body (not as a link), and validate it via a `/verify-otp` endpoint that checks the code and expiry. The current implementation uses none of this. The OTP fields exist but are unused.

This is a confirmed gap. The user's message 5 explicitly says "for signup dont send link to the email just send otp and verify that otp ohk". The verification summary (section "Missing Features", item 1) also flags this: "OTP-based authentication - Current uses email verification tokens. User request: 'for signup dont send link to the email just send otp and verify that otp'. Status: Model has OTP fields but auth flow uses token-based email verification."

**Confidence: confirmed** — the code clearly implements token-based verification, not OTP.
